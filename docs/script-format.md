# 台本の書式規約

## 一話の単位と読み方

**1話＝漫画本文1ページ＝1メッセージ**とします。1ページの中で「誰が、何に困り、何を試し、何が変わったか」が分かり、その回の判断が着地します。複数話を収める Markdown ファイルでも、各話は独立した見出しと区切りを持ちます。

物語の後に、同じ話IDに属する補足を置きます。補足は新しい話として数えません。Webでは漫画ページの後の別枠として読める構成にし、紙面に併載する場合は漫画と補足を合わせた実寸で可読性を検証します。フェーズ1では完成ページや組版済みとは扱いません。

本文に専門用語の定義や説明を入れません。人物は弁当を届けたい、案を認めてもらいたい、間に合わせたいといった欲求から動きます。必要な専門用語が仕事上の台詞に現れる場合も、判断は具体的な物・動き・結果で追えるようにし、説明は補足で行います。

参照の優先順位は README → この規約とストーリーバイブル → 最新稿 `17` → `18`・`19` の設計です。固定設定・通読順・形式・出典情報はそれぞれの元シートを参照します。旧編集ルールの「本文で用語を説明する」等との相違は [整合性メモ](source-notes.md) に記録しています。

## ファイルと話の識別

- フェーズ2では `script/part-01.md`〜`script/part-13.md` に分けます。範囲は [執筆計画](writing-plan.md) と [話IDマニフェスト](../data/writing-manifest.json) に従います。
- ファイル先頭を `# 第N部：アーク名`、各話を `## 話ID / 通読順NNN / タイトル` とします。付録は `# 付録：閉店後の三つの扉` とします。
- タイトルは `17_少年漫画版台本` の採用タイトルを使い、サブタイトルは `01_全話一覧` の原案を保持します。旧タイトルは中間データの履歴として残します。
- 話IDは恒久的な参照キーです。通読順や部が変わっても、REQ-01等のIDを振り直しません。今回の計画は458話を維持します。
- 前後話は全形式での前後と、本編だけの前後を区別します。「次の話へのつなぎ」は原則として全形式の直後を指します。本編だけを読む導線は別欄で示します。

## 標準テンプレート

以下は記入用の型です。山括弧の箇所を置き換えます。台本の完成例ではありません。

```markdown
## <話ID> / 通読順<NNN> / <採用タイトル>

- サブタイトル：<原案を保持>
- 部・アーク：<部番号／部の説明名／アーク名>
- 形式：<本編／技術ノート／比較ノート／付録ガイド>
- 時期・場所：<何か月目／店・部屋／必要な時刻>
- 出演：<人物名（この場面の役割）>
- 制作状態：<コマ割り草稿／推敲中／監修待ち等>

### 制作メモ（読者には表示しない）

- この話の1メッセージ：<一文>
- 主役が欲しいもの：<今回の具体的な目的>
- 今回決まること：<対処・採否・確認範囲・保留条件>
- 伏線・関係変化：<小道具／誰と誰がどう変わるか／前の話ID>
- 引き継ぐ事実：<確定した判断・成果物・残件・次に受け取る人>
- 原案参照：<シート名・行番号／採用箇所／改稿理由>

### 漫画本文（1ページ）

#### コマ1
- 画面指示：<場所・人物の位置・手元の物・視線・動作>
- セリフ：<人物名>「<発話>」
- モノローグ：<人物名>（<内心>）／なし
- 効果音：<音と発生源>／なし

#### コマ2
- 画面指示：<衝突や食い違いが見える動作>
- セリフ：<人物名>「<発話>」
- モノローグ：<人物名>（<内心>）／なし
- 効果音：<音と発生源>／なし

#### コマ3
- 画面指示：<試す行動と、その結果>
- セリフ：<人物名>「<発話>」
- モノローグ：<人物名>（<内心>）／なし
- 効果音：<音と発生源>／なし

#### コマ4
- 画面指示：<今回の決着・関係の変化を見せる手元や表情>
- セリフ：<人物名>「<発話>」
- モノローグ：<人物名>（<内心>）／なし
- 効果音：<音と発生源>／なし

### 次の話へのつなぎ（引き）

- 次話：<話ID / 通読順 / タイトル>
- 渡すもの：<今回の決着から生まれた問い・道具・約束>
- 画面への反映：<最終コマの動作・物・短い台詞で見せる>
- 本編のみの次話：<話ID／該当なし>

### この話で起きていたこと

<どの条件で、誰が何を確かめ、何を選んだかを短く振り返る。>

### ソフトウェアエンジニアリングでは何と呼ぶか

<用語名と短い説明。必要な略語は正式名称と役割を添える。>

### なぜ有効なのか

<今回の問題に効いた仕組みを、場面の行動と結び付けて説明する。>

### どんな場合には使えないか

<成立条件、範囲、費用や負担、別の手段が必要になる場合を示す。>

### SWEBOKではどこで扱われているか

- 基準資料：SWEBOK Guide V4.0a（2025年9月）、<KA番号・名称>
- 対応トピック：<節番号・英語見出し／複数対応は必要なものを列記>
- 節の開始位置：<原書p.章-頁／PDFの1始まりの頁>
- 代表文の位置：<原書p.章-頁／PDFの1始まりの頁>
- 短い要約：<自分の言葉で、原書の主張と条件を要約>
- 物語での具体化：<店舗・事件・数値・手順のどこが独自創作か>
- 対応上の注意：<代表文が支える範囲／未確認点／追加出典が必要な点>
```

標準は4コマを出発点とし、場面に合わせて3〜6コマ程度で試作します。コマ数は本フェーズでの編集上の目安であり、Excelに決められた固定値ではありません。読める大きさの吹き出しと動作を優先し、同じ「先生が答える」構成を反復しません。

## コマと台詞の書き方

画面指示は描ける事実にします。「成長した」ではなく、自分の図を脇に置く、仲間へ札を渡す、手順書を開いてから電話する、といった変化を書きます。場所と人物の役割は、名札・短いキャプション・仕事中の動作など、そのページ内で分かる形にします。

人物は原則2〜3人、合意や共闘の場面は最大5人を目安とします。最新稿にはそれを超える場面もあり、PRO-24では6人が発話します。フェーズ2でコマと吹き出しを試し、必要な役割を残して台詞を整理します。人数を合わせるために引受先を消すことは避けます。

一つのセリフ欄には一人の発話を書きます。複数の発話は同じコマにセリフ欄を追加し、発話順に並べます。電話・画面越しの発話は `水野（電話）「……」` のように発信者を明記します。発話しない場面にも「セリフ：なし」を記入できます。

モノローグは行動で見えない迷いに絞ります。用語説明や作者の結論を内心へ移すことで本文の制約を回避しません。効果音はベル、紙、電話など、何が鳴ったかが分かるようにします。成果物を描く場合は、人物がその図や記録をどう使ったかも示します。

`17` のC〜F列を漫画本文の出発点にし、M〜U列の主題・解説・原文対応は制作メモと補足に使います。V列の通し台本は照合用です。`13` の旧会話を採用する場合は、最新稿から変更した理由を制作メモに残します。

## 引きと単話の決着

引きは、今回の判断で変わった関係や、次に使う道具・記録・問いを渡すものです。読者が次話を開かなくても、今回の小さな問題への対処は分かるようにします。保留を決める回では、確認対象・担当・返答する時点を決着にできます。

引きの欄は制作指示です。読者には最終コマの動作や余韻として見せ、欄の文章をさらに漫画本文へ重複掲載しません。部末には次部へ持ち越す成果物の状態と、受け取る人物を明確にします。

ENG-01（455）は本筋の結末です。付録のAPP-01（456）への案内は任意の後日談として扱い、未解決の昼食を引っ張りません。APP-03（458）は「次話：なし」とし、次の相談へ向かう余韻で閉じます。

## 補足と公開時の出典

五つの見出しは全形式に共通です。技術ノートや比較ノートでも、場面と会話の後に置きます。比較回は比較する条件を一つに絞り、読書会は調べて持ち帰る判断を物語の着地点にします。

補足は短い要約を基本とし、SWEBOK原文の長い転載をしません。英語原文と本教材訳を458話分そのまま公開ページへ流し込みません。全文を保存する `data/episodes.json` と `data/sheets/` はローカル作業用としてGitの対象から外し、公開可能な索引と分割計画を別に出力します。

出典表記の基本形は次のとおりです。

> Hironori Washizaki (ed.), *Guide to the Software Engineering Body of Knowledge*, V4.0a, IEEE Computer Society, September 2025. 第N章 §X.X、原書p.N-x、PDF y頁（1始まり）。公開元：[IEEE Computer Society](https://computer.org/swebok) 。

確認する本文はローカルの `.workspace/swebok-v4.pdf` です。公開元URLは案内先であり、手元と同じ版のPDFを直接指すものとは扱いません。日本語訳は本教材訳であり公式訳ではありません。IEEEによる作品への推奨を示す表現も使いません。

`03_原書トピック`・`10_話と項目の対応` の節開始頁と、`12_原文対照` の代表文の引用頁は区別します。REQ-01なら節開始は原書1-2／PDF44、代表文は原書1-3／PDF45です。一つの代表文で、その話に割り当てた全論点や創作の対処手順を裏付けたとは扱いません。

MTH-19（363）の「補足出典要」を維持します。条件付き確率の定義・公式を書くなら、別の根拠を確認して原書由来と分けて記載します。この段階では補足出典の調査は未実施です。現行の法律・製品仕様・規格の版を扱う話も、執筆時に対象を限定して確認します。

## 文字量と完成の確認

Excelの旧ページ設計は導入60〜100字、物語240〜320字、解説220〜300字、図注40〜60字、結論25〜55字、問い25〜50字、合計610〜885字程度＋図1点です。これは漫画本文・補足を一体で組む旧設計の参考値です。新しい台本に全要素を強制的に詰め込まず、物語の着地と補足の可読性を実寸で確かめます。

フェーズ2では場面と吹き出しを整え、次を満たした状態で漫画化へ渡します。

1. 一話だけで人物の目的・試行・判断が分かり、メッセージが一つである。
2. 台詞が人物の口調と欲求に合い、行動の結果で状況が変わる。
3. 前話で知ったこと、期間、店舗数、責任、成果物の状態が続いている。
4. 補足の成立条件・限界・参照位置を確認し、創作と原書の主張を分けている。
5. コマと吹き出しの実寸を確認できている。未確認なら制作状態に残す。

独立した結論が二つある場合は、まず今回のメッセージへ絞り、関連話や補足へ分けます。話数の変更が必要と判断した場合は、458話のマニフェスト・通読順・原書対応を更新する別の改訂として記録します。今回の初期化では話数を変えません。
