# こはるキッチン
## Koharu Kitchen — A Software Engineering Story

> ソフトウェアエンジニアリングを、物語として読む。

「こはるキッチン」は、ソフトウェアエンジニアリングの知識を、
架空の弁当店チェーン「こはるキッチン」と、そのシステム開発に関わる人々の物語を通して描くプロジェクトです。

要求、設計、実装、テスト、運用、保守、プロジェクト管理――。

これらを用語集や解説書として順番に説明するのではなく、
一つのプロジェクトの中で起こる失敗、衝突、発見、再挑戦を通して描きます。

読者がソフトウェアエンジニアリングの知識を持っていなくても、
まずは一つの仕事の物語、そして登場人物たちの成長物語として楽しめることを目指しています。


## このプロジェクトでやりたいこと

ソフトウェアエンジニアリングには、多くの知識、技法、用語があります。

しかし、実際の開発では、それらを独立した知識として使うわけではありません。

「予約した弁当が受け取れない」
「完成したはずなのに、店では使いづらい」
「テストでは成功したのに、本番では止まった」
「詳しい人がいないと、誰も直せない」

といった具体的な問題に直面し、
その問題を解くために必要な考え方を選びます。

このプロジェクトでは、

**問題に出会う → 悩む → 失敗する → 試す → 仲間とぶつかる → 発見する → もう一度挑む**

という物語の中に、ソフトウェアエンジニアリングの知識を置いていきます。


## 物語として楽しめる教材にする

この作品では、知識を説明するためだけに登場人物を動かしません。

主人公の青井遥には、
「自分の作ったもので人の役に立ちたい」という思いがあります。

けれど、最初は「速く作れば喜んでもらえる」と考え、
現場を十分に知らないまま答えを作ろうとしてしまいます。

そこから、

- 自分より現場を知る店長に負ける
- テスト担当に弱点を見つけられる
- 自分とは違う方法で速く作るライバルと出会う
- 尊敬していた先輩の判断にも限界があると知る
- 自分の作ったものを手放す決断をする
- 一人で解決するのではなく、仲間へ仕事を託す

といった経験を重ねます。

最終的に目指すのは、
「何でも一人で作れるエンジニア」ではありません。

**自分がいなくても、店と仲間が約束を守り続けられる仕組みを作れる人**
へ成長していく物語です。


## 悪役を作らない

この物語には、単純な悪役を置かない方針です。

立場が違えば、守りたいものも違います。

店長には店長の事情があり、
事業責任者には予算を守る責任があり、
テスト担当には失敗を見逃せない理由があり、
運用担当には夜中に呼び出され続けたくない生活があります。

技術的に間違った判断をする人物も、
主人公と対立する人物も登場します。

それでも、

**「なぜ、その人はそう考えたのか」**

が分かる人物として描きます。

対立した相手の強みが、
後になって主人公たちを助けることもあります。

勝敗だけではなく、
相手を理解し、その力を借りられるようになることも
主人公たちの成長として扱います。


## 王道の成長物語として描く

構成は、特定の作品を再現するものではありません。

少年漫画に見られるような、

- 挑戦
- 挫折
- ライバル
- 修業
- 再挑戦
- 仲間との共闘
- 逆転
- 伏線回収
- 師匠との立場の変化
- 次の世代への引き継ぎ

といった物語の推進力を取り入れます。

技術を知っている人物が正解を説明して終わるのではなく、

**人物が実際に行動し、その結果によって状況が変わる**

ことを重視します。


## 一話一メッセージ

各話は、原則として **1ページ1メッセージ** です。

一話だけ読んでも、

- 誰が
- 何に困っていて
- 何を試し
- 何が変わったのか

が分かるようにします。

一方で、最初から続けて読むと、

- 人物関係の変化
- 過去の失敗
- 一度却下された案
- 赤いペン
- 古い台帳
- 一つの注文番号
- 十二時二十分
- 空の弁当袋

といった出来事や小道具が、
後の話で別の意味を持って戻ってきます。


## 「勉強」は物語の後に置く

本文の中では、
可能な限り専門用語の説明をしません。

たとえば、

「同値分割とは〜」
「アーキテクチャレビューとは〜」

という説明から始めるのではなく、

まず登場人物が問題に直面し、
試行錯誤する場面を描きます。

その話を読み終えた後で、

### この話で起きていたこと

### ソフトウェアエンジニアリングでは何と呼ぶか

### なぜ有効なのか

### どんな場合には使えないか

### SWEBOKではどこで扱われているか

といった補足を読む構成にします。

物語だけ読んでも楽しめる。

補足まで読むと、
「あの場面には、こういう一般化できる考え方があったのか」
と分かる。

その二段構成を目指します。


## SWEBOKとの関係

本プロジェクトでは、
IEEE Computer Society の

**Guide to the Software Engineering Body of Knowledge (SWEBOK Guide) V4.0a**

を主要な知識体系の一つとして利用します。

SWEBOKの章立てを、そのまま物語の章立てにはしません。

物語は、
「こはるキッチンで実際に何が起きたのか」
という時間軸で進みます。

そのうえで各話について、

- 対応するKnowledge Area
- 対応するトピック
- 英語原文
- 日本語訳
- 引用位置
- 物語での具体化
- 原文には含まれない創作部分

を対応付けて管理します。

物語上の出来事や人物の判断を、
SWEBOKそのものに書かれている内容であるかのようには扱いません。


## 主な舞台

### こはるキッチン / Koharu Kitchen

複数店舗を展開する弁当店。

電話や紙の台帳を使った予約業務を改善するため、
新しい注文システムの導入を始めます。

開発が進むにつれ、

- 予約
- 在庫
- 決済
- 店舗ごとの違い
- 昼の混雑
- 障害
- 運用
- 保守
- 店舗展開
- 外部サービスとの連携

など、最初には見えていなかった問題が次々に現れます。


## 物語の出発点

十二時二十分。

予約していた最後の一食が、
別のお客さんに売られてしまいます。

若手開発者・青井遥は、
すぐに在庫を管理する画面を作ろうとします。

しかし予約客から言われます。

> 「その画面から、お弁当が出てきます？」

ここから物語が始まります。

「何を作るか」ではなく、

**「本当に解かなければならない問題は何か」**

を探す十八か月です。


## ゴール

このプロジェクトのゴールは、
SWEBOKの内容を暗記できる教材を作ることではありません。

読者が物語を読み終えたあと、

- 問題をすぐ技術へ置き換えない
- 相手によって見えているものが違う
- 一つの正解ではなく、条件に合う選択を探す
- 失敗を隠すより、次に使える形で残す
- 技術だけでなく、人、運用、費用まで含めて考える
- 自分一人が詳しい状態を完成とは呼ばない

といった考え方を、
登場人物たちの経験として思い出せる状態を目指します。

そして必要になったとき、

「そういえば、こはるキッチンで似たことが起きていた」

ところから、
正式な用語、標準、書籍、技法へ進める作品にします。

## リポジトリ構成

- `data/`：Excelから抽出した中間データ、全458話の索引、部ごとのファイル分割計画。
- `art/`：人物・背景・小道具・キービジュアルの美術設定画像。
- [art/v2/](art/v2/)：連載版の画風による人物・背景の美術設定画像。
- `docs/`：ストーリーバイブル、台本の書式規約、執筆計画、出典と整合性の確認記録。
- [docs/craft/](docs/craft/)：物語づくり・漫画技法・画風の調査。
- [docs/serial/](docs/serial/)：週刊連載版の方向性・全体構成・第1〜3話シナリオ・査読記録。
- `docs/art/`：[美術設定の目次](docs/art/README.md)と、世界観・人物・舞台・小道具・画風の設定文書。
- [docs/art/v2-style.md](docs/art/v2-style.md)：連載版の画風・作画仕様。
- `script/`：全458話の台本本体。フェーズ2bで統合した13部のファイルを正本とします。
- `manga/`：漫画画像と[読むための目次](manga/README.md)。
- [manga/serial/ch01/](manga/serial/ch01/)：連載版第1話「その一食を、取り戻せ」全46ページ。[連載版第1話を読む](manga/serial/ch01/README.md)。
- `manga/part-01/`：旧画風の試作。第1部「腹ぺこの約束」の扉・本文8ページ・ネーム・制作記録。[試作を読む](manga/part-01/README.md)。
- [manga/pages/](manga/pages/)：旧画風の試作。代表場面の漫画8ページ。
- `tools/`：Excel抽出、台本の統合・検証・目次生成スクリプト。
- `.workspace/`：入力のExcelと参照PDF。Git管理の対象外です。

設計資料は [ストーリーバイブル](docs/story-bible.md)、[台本の書式規約](docs/script-format.md)、[全458話の執筆計画](docs/writing-plan.md) にあります。
台本は [全話目次と読み方](script/README.md)、フェーズ2bの確認結果は [通し校閲記録](docs/continuity-review.md) を参照してください。
抽出の実行方法と、原文・訳を含むローカル作業用データの扱いは [data/README.md](data/README.md) を参照してください。
